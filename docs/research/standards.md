# Research: EDI standards, licensing and French e-invoicing

> Research snapshot of **2026-10-17**. Facts marked *(unverified)* could not be read on a
> primary source. This is not legal advice.

## 1. UN/EDIFACT essentials

### Interchange structure

`[UNA] UNB … [UNG … [UNH … UNT]… UNE] … UNZ`

- **UNA** (optional) declares six service characters, in order: component separator `:`,
  element separator `+`, decimal mark `.`, release character `?`, repetition separator
  (`*` in syntax 4, a reserved space in syntax 3), segment terminator `'`.
- **UNB** carries the syntax identifier (`UNOC:3`), sender and recipient (GLN with
  qualifier `14`), date/time, interchange control reference (0020), acknowledgement
  request (0031 = `1`), agreement identifier (0032; EANCOM requires it to start with
  `EANCOM`) and the **test indicator (0035)**, which maps naturally to Ediflux's test
  environment.
- **UNG/UNE** functional groups are optional and rare in retail.
- **UNH/UNT** frame each message. UNH holds the message reference and identifier, e.g.
  `ORDERS:D:01B:UN:EAN010` (type, directory, release, agency, GS1 subset). UNT repeats the
  reference with the segment count. **UNS** separates header, detail and summary.
- Escaping with the release character; trailing empty elements may be truncated; numbers
  use the declared decimal mark with no thousands separator; parsers must tolerate CR/LF
  after the segment terminator.

### Syntax versions and character sets

- ISO 9735 versions 1 (1988), 2 (1990), 3 (1992), 4 (1998; repetition separator, UGH/UGT,
  security, CONTRL integrated in the syntax). The v4 parts are paid ISO documents; the v3
  rules are published by UNECE.
- In France, EANCOM 1994/1997/2002 are used **with syntax 3**; syntax 4 is rare.
- Character sets: UNOA (EANCOM default, uppercase), UNOB (adds lowercase), UNOC
  (ISO 8859-1, covers French), UNOD–UNOK (ISO 8859-2…9), UNOW (UTF-8), UNOY (ISO 10646).
  Ediflux must support at least **UNOA, UNOB, UNOC and UNOW**, reading UNB up to S001 as
  ISO 646 before switching.

### Directories

- **EANCOM 1997 = D.96A** (syntax 3), **EANCOM 2002 = D.01B** (syntax 3 and 4). Retail EDI
  in Europe means these two; where both exist, most users are still on 1997 (GS1 survey).
- Newer directories (D.16B, D.21B, D.24A) exist but are not retail baselines.
- Download page: <https://unece.org/trade/uncefact/unedifact/download>.

### Acknowledgements

- **CONTRL**: syntax-level, generated by the receiving translator, per interchange or per
  message; requested with UNB 0031 = 1 or by agreement.
- **APERAK**: application-level, optional, by agreement.
- **AS2 MDN**: transport-level receipt, independent of the two above.
- In retail, ORDRSP and RECADV often act as business acknowledgements *(unverified)*.

## 2. Licensing constraints (critical for an AGPL project)

| Material | Terms | Consequence for Ediflux |
|---|---|---|
| **UN/EDIFACT directories** (D.01B, D.16B, D.21B zips contain `LICENAGR.TXT`) | Use limited to the licensee's country; redistribution of the **unmodified** zip with its licence is allowed; **modifying and distributing** is not, without written UN permission. D.96A: "all rights reserved". | **Do not commit or ship derived directory data** (JSON, XSD, SQL) in the repo, releases or images. Ship a generator that downloads the official zips on first run into the operator's volume, so the operator is the licensee. Optionally ask UNECE for written permission. |
| **EANCOM (GS1)** manuals, GS1 France profiles | Copyright GS1; reproduction only unaltered, personal or internal; no redistribution without written approval. EANCOM® is a registered trademark. | Do not bundle GS1 documents, profiles or machine-readable EANCOM subsets. Partner mappings are user content. Use "EANCOM" only descriptively. |
| **ANSI X12** dictionaries, code sets, schemas | Copyrighted; distribution of derived works or use in a commercial product needs an X12 licence (Developer $1,200/yr, Internal $3,600/yr, Commercial partner by agreement). | Defer X12. When added: envelope parser plus **user-supplied** schemas only, as StAEDI does. |
| **UN/CEFACT CII XSDs** (D22B) | Copy, derive and distribute freely with the notice kept. | Can be shipped. |
| **UBL 2.1** (OASIS) | Royalty-free, schemas must not be modified. | Can be shipped unmodified. |
| **EN 16931 validation artefacts** | EUPL-1.2. | Compatible with AGPL. |
| **AFNOR XP Z12-013** (PA API) | Free PDF but copyrighted; AFNOR forbids redistribution and processing by AI tools. | Implement the client by hand; never commit the PDF or feed it to AI tools. |

Precedents: Smooks ships the original UNECE zips and generates schemas at build time;
pydifact ships generated XML for recent directories. Whether they obtained UN permission is
unknown, so they are precedent, not permission.

## 3. Message priorities for a supplier selling to large retail

The order, despatch advice and invoice represent more than 90 % of retail EDI transactions
in France (GS1 France / Generix, 2018); France counts about 15,500 EANCOM users.

| # | Message | Purpose | Supplier direction |
|---|---|---|---|
| 1 | ORDERS | Purchase order | inbound |
| 2 | DESADV | Despatch advice (SSCC) | outbound |
| 3 | INVOIC | Invoice / credit note | outbound (see §5) |
| 4 | ORDRSP | Order response | outbound |
| 5 | RECADV | Receiving advice | inbound |
| 6 | ORDCHG | Order change | inbound |
| 7 | PRICAT | Price/sales catalogue | outbound |
| 8 | INVRPT, SLSRPT | Stock and sales reports | outbound |
| 9 | REMADV | Remittance advice | inbound |
| 10 | PARTIN | Party and location data | both |
| 11 | IFTMIN | Transport instruction | outbound to carriers |

**MVP**: ORDERS in, ORDRSP out, DESADV out, CONTRL in/out. **Wave 2**: INVOIC through a
PA, RECADV, ORDCHG. **Wave 3**: PRICAT, INVRPT/SLSRPT, PARTIN, REMADV, IFTMIN.

## 4. Other syntaxes and transports

| Syntax | Relevance in France |
|---|---|
| UBL 2.1, UN/CEFACT CII D22B, Factur-X | **High**: the three base formats of the French e-invoicing reform |
| Peppol BIS Billing 3.0 | Medium: interoperability layer between platforms |
| ANSI X12 | Low (multinationals); licensing constraints above |
| ODETTE / VDA | Automotive only |
| TRADACOMS | UK only, unsupported by GS1 UK since 2017 |
| GS1 XML, cXML | Low (cXML for Ariba buyers) |

| Transport | Who uses it | Priority |
|---|---|---|
| SFTP | Very common; also one of the PA↔PPF protocols | **High** |
| AS2 (RFC 4130, signed MDN) | Most popular EDI channel worldwide; used in France next to VANs | **High** |
| HTTPS / REST | PA APIs (AFNOR XP Z12-013), ERP webhooks | **High** |
| AS4 (ebMS 3, Peppol) | Peppol, PA↔PA | Medium, rising |
| FTPS / FTP | Legacy partners | Medium / low |
| Email | Small-partner fallback | Low / medium |
| OFTP2 | Automotive | Low |
| X.400 | Legacy retail networks (Atlas 400, Allegro) *(current status unverified)* | Low: reach through a VAN's AS2/SFTP bridge |

## 5. French B2B e-invoicing reform (status October 2026)

- **Calendar** (art. 91 LF 2024, confirmed by the DGFiP in September 2026):
  - since **1 September 2026**, every VAT-liable company must be able to **receive**
    e-invoices through a *plateforme agréée* (PA); large companies and ETI must **issue**;
  - from **1 September 2027**, SMEs and micro-enterprises must issue;
  - e-reporting follows the same calendar, through the PA.
- **Penalties** (LF 2026): €50 per non-compliant invoice (capped at €15,000 per year);
  €500 then €1,000 per quarter for not using a PA for reception; €500 per missed
  e-reporting transmission.
- **PPF** is now only the directory (routing) and the data concentrator for the tax
  administration. More than 130 PAs are registered.
- **Base formats** (AFNOR XP Z12-012): UBL 2.1, UN/CEFACT CII D22B, Factur-X.
- **EDIFACT INVOIC** between French VAT-registered companies remains possible **only inside
  a PA circuit**, if the sender's PA supports it, carrying the regulatory data; the buyer's
  PA may convert it. Direct bilateral or VAN-to-VAN exchange no longer satisfies the law for
  in-scope invoices.
- **Orders, despatch advices and other non-invoice documents are not affected**: they keep
  being exchanged as the partners choose.
- **Becoming a PA** requires DGFiP registration, ISO 27001, EU hosting, SecNumCloud-grade
  infrastructure, annual audits and a link to the PPF. Ediflux will not be a PA.
- **EU ViDA** (Directive 2025/516): cross-border B2B e-invoicing and digital reporting from
  1 July 2030.

## Implications for Ediflux

1. **No derived UN directory data in the repository or images.** A directory generator
   downloads the official UNECE zips on first run. MVP message definitions are written by
   hand from the directory structure, without copying GS1 material.
2. **Partner and EANCOM specifics are user content** (mapping packs), never bundled.
3. **X12 later, with user-supplied schemas only.**
4. **MVP messages**: ORDERS in, ORDRSP out, DESADV out, with CONTRL, on D.96A and D.01B,
   syntax 3 first.
5. **Transports MVP**: SFTP and HTTPS first, AS2 with MDN next, AS4 later, OFTP2/X.400 via
   a VAN bridge or never.
6. **Never claim to be a PA**, never use "plateforme agréée" wording or the DGFiP mark.
   Ediflux can generate Factur-X/UBL/CII, hand invoices to the customer's PA through its API
   (AFNOR XP Z12-013) and receive invoices from it. It must not send in-scope domestic
   invoices directly to buyers, nor transmit to the PPF.
7. **Invoices need enrichment** (SIREN, operation type, delivery address) that a standard
   EANCOM INVOIC may lack *(inference)*.
8. **Hosted offer** in the EU, routing invoices through each customer's PA; ISO 27001 is not
   legally required but customers will ask for it.
